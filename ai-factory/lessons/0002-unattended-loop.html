LESSON 0002 · AIファクトリー

無人で1機能ずつ回す

ファクトリーの心臓は、30行ほどのループだ。難しいのは回すことより、正しく止める ことのほうにある。

claude -p を毎回新しいセッションで呼ぶループを自分のマシンで1回動かす。そして、そのループを守る 4つのガード が、それぞれどの失敗を止めるのかを言えるようになる。

0. 前回の復習（見ないで答える）

時間を空けて思い出すと、記憶に定着する。

R1. コーディングエージェントがセッションの始めに、新しい機能より先にやることは？
R2. 「次のセッションが前の続きから始められるようにする」部品は？

1. お手本のループを読む

Anthropic は、記事の実装を claude-quickstarts/autonomous-coding として公開している[1]。中心にあるのは agent.py のループで、骨組みは次のとおりだ。

is_first_run = not feature_list.json が存在する
while True:
    if max_iterations に達した: break
    client = create_client(...)          # ← 毎回新しいコンテキスト
    prompt = 初期化用 if is_first_run else 続き用
    is_first_run = False
    セッションを実行
    3秒待って次へ

見てほしい点は3つある。

  1. セッションごとにクライアントを作り直す。 長い会話を続けるのではなく、毎回まっさらなコンテキストで始める。続きは feature_list.json・claude-progress.txt・git が引き継ぐ[2]。
  2. どちらのプロンプトを使うかは、機能一覧があるかどうかで決まる。 機能一覧がなければ初期化エージェントになる。初期化エージェントの仕事は、その一覧を作ることだ。
  3. 止まる条件は max_iterations だけ。 全機能が通っても、ループは自分では止まらない。デモなら十分だが、自分のファクトリーにするならガードを足す必要がある。
Q1. 1つの長い会話ではなく、毎回新しいセッションで始めるのはなぜ？
Q2. お手本は、初期化と続きのどちらのプロンプトを使うかを何で決めている？

2. Claude Code で組み直す：4つのガード

お手本は Python の Agent SDK で書かれている。同じことは claude -p でもできる。-p を付けると対話なしで1回実行し、終わればプロセスごと終了する。つまり、呼ぶたびに新しいセッションになる[3]。スターターキットの factory.sh は、これに次の4つのガードを足している。

ガード止める条件防ぐ失敗
完了判定passes: false が0件全部終わったのに回り続け、お金を使い続ける
回数上限MAX_ITER 回に達した終わりのない実行
停滞検知残り件数が MAX_STALL 回続けて減らない同じ失敗を朝まで繰り返す
改竄検知passes 以外のフィールドが変わった難しいテストを書き換えて「合格」にする

改竄検知は、プロンプトの「書き換えるな」を 機械的に強制する ものだ。OpenAI のチームも、アーキテクチャの決まりをレビューに頼らず、linter と構造テストで強制している[4]。エージェントへのお願いは破られることがある。チェックは破られない。

それぞれのセッションには --max-budget-usd で費用の上限もかける。--output-format json を付けると、結果に total_cost_usd が入るので、1回ごとの費用をログに残せる[3]。

claude -p "$(cat prompts/coding.md)" \
  --permission-mode auto --permission-prompts none \
  --max-budget-usd "$SESSION_BUDGET" \
  --output-format json > ".factory/session-$i.json"

--permission-prompts none を付けると、誰も答えられない許可の確認で待ち続けず、その操作を断って先へ進む。無人で動かすときのためのオプションだ[3]。

練習：どのガードが止める？

Q3. エージェントが難しい機能の steps を簡単なものに書き換え、passes: true にした。
Q4. 毎回同じエラーで失敗して、残り件数が減らないまま朝になっていた。
Q5. 全機能が通ったのに、ループが回り続けてトークンを使い続けた。
Q6. 1回のセッションの中でエージェントが同じことを延々と試し、それだけで想定の10倍の費用がかかった。

3. 実際に1回まわす

スターターキットは ai-factory/starter/ にある。小さな TODO 用 CLI の機能が4つ、機能一覧に入っている。今回は 人間が機能一覧を書いた ので、初期化エージェントは使わない（機能一覧があれば続きのプロンプトから始まる。Q2 と同じ理屈だ）。このリポジトリの中では動かさず、使い捨てのフォルダで試す。

mkdir -p ~/workspace/factory-sandbox && cd ~/workspace/factory-sandbox
git init
cp -r ~/workspace/project_setup/ai-factory/starter/. .
git add . && git commit -m "仕様と工場を置く"
MAX_ITER=1 ./factory.sh

終わったら、次の3つを確かめる。これがあなたの最初の「検品」になる。

  1. git log --oneline：エージェントが説明つきのコミットを残したか
  2. cat claude-progress.txt：次のセッションへの引き継ぎが書かれているか
  3. feature_list.json で true になった機能の steps を 自分で実行 し、本当に expected のとおりになるか

うまくいったら MAX_ITER=5 ./factory.sh で最後まで回してみる。かかった費用は .factory/session-*.json に残る。

動かす前に予想してみる：このキットの一番弱いところはどこ？

検品を、エージェント自身の自己申告に頼っている ところだ。passes: true にするのはエージェント本人で、ループが確かめているのは「機能一覧の数字が減ったか」だけ。steps を実行して expected と照らし合わせる仕組みは、ループの側にはない。StrongDM がシナリオをエージェントから隠すのも、この問題があるからだ（レッスン 0001 の Q6）。次のレッスンでは、この検品を機械にやらせる。

一次資料を読む： prompts/coding_prompt.md（Anthropic）。スターターキットの prompts/coding.md は、これを短くして日本語にしたものだ。原文の「STEP 3: VERIFICATION TEST」と「STEP 7」が、どれだけ強い言葉で書かれているかを見てほしい。
わからないところは Claude に聞いてほしい。たとえば「--permission-mode auto は何を許して、何を止める？」「停滞検知の MAX_STALL はいくつが妥当？」「実行してみたらこうなった。どう読めばいい？」など。実行ログをそのまま貼ってもらえれば一緒に読む。
