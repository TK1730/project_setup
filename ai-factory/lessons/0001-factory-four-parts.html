LESSON 0001 · AIファクトリー

工場の4つの部品

AIファクトリーは「賢いエージェント」ではなく「エージェントを取り囲む仕組み」でできている。まず、その仕組みを4つの部品に分けて見えるようにする。

どんなファクトリーの記事やツールを見ても、それが 仕様・実行・検品・記録 のどの部品の話なのかを分類できる。さらに、自分の scripts/harness/ がどの部品をすでに持っているかを言える。

1. 今どこにいて、どこへ向かうのか

Dan Shapiro は、AI を使った開発をレベル0〜5に分けた[1]。上のレベルほど、人間はコードから離れる。

Lv状態人間の役割
2AI と組んで、フローに入って書くまだ自分が運転している
3複数のエージェントが書き、人間は diff を読むマネージャー兼レビュアー
4仕様を書いて数時間走らせ、テストが通ったか確認する仕様を書き、結果を検証する PM
5ダークファクトリー：仕様がソフトウェアになるブラックボックス工程に人間はいない

あなたは今 2〜3 にいる。このコースの目標は レベル4の個人ファクトリー だ。StrongDM はレベル5を実践しているが[2]、トークン代は「エンジニア1人1日 $1,000 以上」が目安だという[2]。個人開発の予算では、目標は4で十分だ。

2. ファクトリー ＝ モデル ＋ ハーネス

OpenAI の Codex チームは、手で書いたコードなしでプロダクトを作った。そのとき人間の仕事は、コードを書くことから 「環境を設計し、意図を伝え、フィードバックの仕組みを作る」 ことに変わったという[3]。モデルの周りにあるこの環境を ハーネス と呼ぶ。

Anthropic は、何時間も動くエージェントの根本的な問題を一文で書いている。エージェントは別々のセッションで動き、「新しいセッションは、前に何があったかの記憶なしで始まる」[4]。だからファクトリーは、記憶のない作業員が交代しても仕事が進むように設計しなければならない。そのために次の4つの部品が要る。

① 仕様何を作るか、そして「完了」とは何か。例：機能一覧の JSON。全項目を「未達成」から始める。
② 実行人間なしでエージェントを動かすライン。例：claude -p、worktree で並列化、初期化エージェントとコーディングエージェント。
③ 検品エージェントの「できました」を信じてよいか確かめる。例：E2E テスト、エージェントに見せないシナリオ。
④ 記録次のセッションが前の続きから始められるようにする。例：進捗ファイル、説明つきの git コミット、docs。

なぜ4つとも必要か：Anthropic が見た失敗

Anthropic の実験では、部品が欠けるたびに決まった失敗が起きた[4]。

起きた失敗欠けていた部品
一気に全部作ろうとして、途中でコンテキストが尽きる① 仕様（1機能ずつに分けていない）
後のエージェントが進捗を見て「もう完成」と宣言する① 仕様（「完了」の定義がない）
テストせずに機能を完了にする③ 検品
作りかけの機能が説明なしで残る④ 記録
アプリの起動方法を毎回調べ直して時間を無駄にする② 実行（init.sh がない）

検品はいちばん難しい部品だ。StrongDM は、エージェントがテストを「ズルして」通すことを防ぐために、E2E のユーザーストーリー（シナリオ）を コードベースの外 に置く。機械学習の「ホールドアウト」データと同じ考え方だ[2]。Simon Willison は、人間が全行を読まずにコードが動くことをエージェントに証明させる方法を、今のソフトウェア開発で最も重要な未解決問題の一つだと書いている[2]。

3. 練習：部品を分類する

答える前に、上の4つのカードを見ないで思い出してみる。そのほうが記憶に残る。

Q1. ユーザーの一文の依頼を、200以上の機能に展開した feature_list.json
Q2. claude-progress.txt（各セッションの作業ログ）
Q3. git worktree を3つ作り、それぞれで claude -p "…" --permission-mode auto を起動するスクリプト
Q4. あなたの scripts/harness/probe.sh（同じ依頼を変更前と変更後のハーネスで実行して比べる）
Q5. Anthropic が機能一覧を Markdown ではなく JSON で書いた理由は？
Q6. StrongDM がシナリオをコードベースの外に置く理由は？
Q7. 「朝に仕様を書いて夜まで走らせ、帰ってきたらテストが通ったかだけ確認する」。これは Shapiro のどのレベル？

4. 自分のリポジトリに当てはめる

この演習は答えを確かめず、自分の言葉で書く。scripts/harness/ の3つのスクリプト（probe.sh・docs_check.py・clarify_report.py）と docs/AGENTS.md を、4つの部品に振り分けてみる。まだ何もない部品 はどれか。

書いたら開く：先生からの見立て

probe.sh は ③ 検品（ハーネスの変更を検証する）。docs_check.py は docs を機械的にチェックするので ④ 記録の品質を保つ部品だ。OpenAI も、docs のリンクや整合性を linter と CI で強制している[3]。docs/AGENTS.md はエージェントへの地図で、④ 記録の一部。

いちばん手薄なのは、おそらく ① 仕様（機能一覧と「完了」の定義）と ② 実行（1機能ずつ無人で回すループ）だ。次のレッスンでは、ここを作る。違う考えなら、ぜひ教えてほしい。

5. 閉じる前に

何も見ずに：4つの部品と、それぞれが防ぐ失敗を1つずつ言えるか？

① 仕様：一気に作ろうとする失敗、早すぎる「完成」宣言 ／ ② 実行：起動方法を毎回調べ直す、人間が張り付く必要がある ／ ③ 検品：テストなしで完了にする、テストをズルして通す ／ ④ 記録：作りかけのまま説明なしで終わる、次のセッションが状況をつかめない

一次資料を読む： Anthropic「Effective harnesses for long-running agents」。このレッスンの ①②④ のほとんどはこの記事から来ている。15分ほどで読める。読んだら、初期化エージェントとコーディングエージェントの違いを説明できるか試してみる。
わからないところ、納得できないところは、そのまま Claude に質問してほしい。たとえば「feature list の passes を、エージェント自身が true にしてよいのはなぜ？」「自分のリポジトリだと、どこに仕様を置くべき？」など。先生役はこのセッションの Claude だ。
