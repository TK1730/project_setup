# 文書の種類と置き場所

伝えたいことを、どの種類の文書に書くかの基準。コードに近い手段で伝えられることは、そちらで伝える。

## 種類の一覧

コードに近いものから順に並べる。上の手段で伝えられることは、下の手段に回さない。

1. 意味のある名前: 変数からディレクトリまで、名前で伝えられることはコメントや文書に回さない。
1. インラインコメント: コードだけでは表せないこと（なぜそのコードがあるか）だけを書く。下の「インラインコメントの書き方」を参照。
1. メソッド・クラスのコメント: 下の「doc comment の書き方」を参照。
1. テスト: 振る舞いの具体例、境界値、注意点。下の「テストで振る舞いを示す」を参照。
1. `README.md`: ディレクトリの案内役。書き方は [README の書き方](/guides/readme.md) を参照。
1. `docs/` ディレクトリ: 設計、仕様、使い始め方、テストの実行、デバッグ、リリースの方法を書く。
1. 設計文書・PRD: 実装後は決定の記録として扱う。半分だけ正しい仕様書として使わない。
1. 外部の文書（wiki など）: 使う場合は、プロジェクトの `README.md` などから明確にリンクする。

## コードコメント

コメントは、処理を説明するインラインコメントと、関数・型・ファイルを説明する doc comment（JSDoc や Go の doc comment）の 2 種類に分けて扱う。インラインコメントは少なく保ち、doc comment には関数・型の約束だけを書く。振る舞いの詳細の正はテストとする。

### インラインコメントの書き方

インラインコメントの書き方は、[コードを書くときに意識すること](/knowledge/coding-mindset.md) の「コメントより読みやすいコードを優先する」に従う。要点は、まず名前と構造で意図を伝え、コメントには「なぜそうしたか」だけを書くことである。

### doc comment の書き方

- メソッドのコメントには、関数の約束として、目的、引数、戻り値、返すエラーの種類を書く。
- 境界値や注意点などの振る舞いの詳細は、doc comment に書かずテストに書く。
- クラスやファイルのコメントには、概要と短い使用例を書く。最も単純な使い方を先に置く。
- 複数のファイルにまたがる全体像を docs に書くときは、[コードを説明する文書の書き方](/guides/code-docs.md) の型に従う。関数ごとの約束はコメントに、振る舞いはテストに残し、docs には写さない。

### テストで振る舞いを示す

テストの書き方は、[コードを書くときに意識すること](/knowledge/coding-mindset.md) の「テストを実行できる仕様書として書く」に従う。要点は、振る舞いの具体例・境界値・注意点をテストに書き、テストの名前を振る舞いを表す文にすることである。テストの構成は [テスト設計における AAA パターン](/knowledge/aaa-pattern.md) と [テーブル駆動テストの設計指針](/knowledge/table-driven-tests.md) を参照する。

## 既存の文書を書き直さない

- 既にある共通の手順や技術の文書を、自分で書き直さない。リンクする。
- 無い、または古い場合は、既存の場所を更新するか、パッケージ単位の `README.md` を作る。
