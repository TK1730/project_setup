# コードを説明する文書の書き方

機能やライブラリを説明する文書（`type: spec`）の型。目的は、そのコードを初めて見る人が、コードを開く前に「どう振る舞うか」と「どこから読めばよいか」を理解できることである。関数ごとの約束はコードのコメントに、振る舞いの詳細はテストに任せ、docs には複数のファイルにまたがる全体像だけを書く。

## 書く場所の分担

同じことを 2 か所に書くと、片方だけが古くなる。次の表で書く場所を 1 つに決める。

| 書く場所                  | 書くこと                                                       | 正とするもの     |
| :------------------------ | :------------------------------------------------------------- | :--------------- |
| JSDoc / Go の doc comment | 関数・型ごとの約束。目的、引数、戻り値、返すエラーの種類       | 関数単位の約束   |
| テスト                    | 振る舞いの具体例、境界値、注意点。名前を振る舞いを表す文にする | 振る舞いの仕様   |
| `openapi.yaml`            | HTTP API のパス、リクエスト、レスポンス                        | HTTP API の仕様  |
| マイグレーション          | テーブルの実際の定義                                           | DB の定義        |
| docs（この型の文書）      | 目的、用語、構成と読む順番、全体の流れ、状態遷移、設計の理由   | 全体像と「なぜ」 |

docs には次のものを書かない。必要なら、正とする場所へリンクする。

- 関数のシグネチャ、引数と戻り値の一覧、型定義の写し。
- テストケースの一覧。
- 実装コードの抜粋。仕組みの説明に必要な場合は、疑似コードか図にする。

## コードを説明する文書の骨子

[文書の構成](/guides/document-structure.md) の標準骨子を、次のように具体化する。各見出しの `<対象>` には機能名やライブラリ名を入れる。当てはまる内容が無い節は省く。

```markdown
---
type: spec
（ほかのキーは Open Knowledge Format 運用ガイドに従う）
---

# <対象>

<対象> が何をするものかを 1〜3 文で書く。

## <対象> でできること・できないこと

## <対象> の用語

## <対象> の構成と読む順番

## <対象> の振る舞い

## 決定理由（Rationale）

## See also
```

### 「できること・できないこと」の節

使う人から見た振る舞いを、箇条書きで書く。内部の仕組みではなく、外から観察できる結果を書く（例: 「動作中はリセットできない」）。対象外にしたことも書く。

### 「用語」の節

この文書とコードで使う言葉を、日本語名・コード上の名前・説明の表にする。コード上の名前（`elapsedSeconds` など）を併記すると、読者がコードを検索できる。

### 「構成と読む順番」の節

関わるファイルを、読むべき順に番号付きリストで並べる。各項目には、そのファイルが負う責務と負わない責務を 1〜2 文で書く。ファイルへは相対パスでリンクする。

パッケージが 3 つ以上あるときは、リストの前にコンポーネント図を置き、どのパッケージがどれを呼ぶかを矢印で示す。Mermaid にはコンポーネント図の専用の書き方がないので、`flowchart` の `subgraph` でパッケージを囲んで描く。

### 「振る舞い」の節

この型の中心となる節。次の中から、対象に合うものを選んで書く。

- 全体の流れ: 利用者の操作から結果までを、Mermaid のシーケンス図で書く。
  - バックエンドの図は、その機能の Handler から描く。ルーターなど、すべての機能に共通する経路は `docs/<領域>/architecture.md` に 1 か所だけ書き、図の下からリンクする。
  - 分岐（行がある・ないなど）は、シーケンス図の `alt` で示す。
- 状態遷移: 状態を持つものは、Mermaid の状態遷移図で書く。各遷移には、そのとき起きる副作用（API 保存など）を添える。
  - 状態を変えない操作（GET など）には、状態遷移図を描かない。自分に戻る矢印だけの図になり、伝えることがない。
  - 同じ操作の矢印が何本もあると、続けて何回も送る流れに読まれる。図の前に「1 回送ったときに、送る前の状態ごとにどうなるかを表す」と書き、ラベルに送る前の状態を入れる（例: 「行があるときの DELETE（行を消す）」）。
- 入力と結果の具体例: 「この入力のとき、こうなる」を表で示す。全体像の理解に必要な代表例と境界値（0、上限、時計の逆行など）に絞り、網羅的な一覧はテストに任せる。
  - API なら、結果の表（ステータスコードごとに何が起きるか）に加えて、送る本文と返る応答の JSON の例を載せる。時間などの単位と、エラーの応答の形（JSON か文字列か）も書く。
- 注意点: 初めての人がつまずく振る舞いを書く。1 つの関数で閉じる注意点はその関数のテストに書き、ここには複数のファイルにまたがるものだけを書く。

### 機能が大きいとき

1 つの機能に操作が 3 つ以上あり、1 つの文書では読みにくいときは、`docs/<領域>/features/<機能名>/` のディレクトリにして、概要と操作ごとの文書に分ける。

| 文書 | 書くこと |
| :-- | :-- |
| `overview.md` | できること・できないこと、用語、操作を比べる表（各操作の文書へのリンク付き）、コンポーネント図と読む順番、機能全体に関わる決定理由 |
| 操作ごとの文書（`get.md` など） | 結果の表、送る本文と応答の例、シーケンス図、その操作で状態が変わるなら状態遷移図、注意点、その操作だけに関わる決定理由 |

操作ごとの文書は、時間が経ってから仕様を振り返る人が最初に開く文書である。その文書だけで「何を送ると何が返るか」と「なぜそうしたか」が分かるようにする。

### 振る舞いを正確に書く

読者は書かれたとおりに信じるので、振る舞いは誇張せずに書く。

- 「完全に」「誤差ゼロ」のような言い切りを避け、実際の挙動と限界を書く（例: 「残り時間は毎回実時刻から計算し直すので、誤差が累積しない。表示の更新は `setInterval` の遅れの分だけ遅れる」）。
- 丸めや切り捨ては、どの関数がどちらを使うかを書く。
- 分からないことは推測で書かず、コードかテストで確かめてから書く。

## API と DB テーブルへのリンク

コードが呼ぶ API から、その API の仕様、さらにその API が読み書きする DB テーブルまで辿れるようにする。コード、`openapi.yaml`、マイグレーションなど docs の外のファイルにも、GitHub 上で辿れる相対パスならリンクしてよい。リンクを張っても、相手のファイルが変わったことは docs に伝わらない。そのため、API を変えたら同じ変更で docs も直す。

- 層をまたぐ鍵は `openapi.yaml` の `operationId` とする（例: `createPomodoro`）。フロントの関数名と Go のハンドラ名も同じ名前に揃っているので、リンクが無くても全文検索で各層が見つかる。
- 機能の文書では、「振る舞い」の節で API が登場する箇所に、`openapi.yaml` へのリンク、`operationId`、テーブルの文書へのリンクを書く。
- テーブルの文書には「このテーブルを使う API」の節を置き、`operationId` と `openapi.yaml` へのリンクを並べる。これで、テーブルから API へ逆向きにも辿れる。
- `openapi.yaml` へのリンクはファイル単位にする。`#L20` のような行番号付きのリンクは、行がずれると切れるので使わない。

```markdown
一時停止すると、区間を `POST /api/pomodoros`（`operationId: createPomodoro`）で保存する。
仕様は [openapi.yaml](../../../openapi/openapi.yaml)、保存先は [pomodoro_records](/database/pomodoro-records.md) を参照する。
```

API を追加・削除したら、同じ変更で機能の文書とテーブルの文書のリンクも直す。

## コードを説明する文書のレビュー観点

レビューでは、次の問いに文書だけで答えられるかを確かめる。答えられなければ、足りない節を足す。

1. このコードは何のためにあり、何をしないか。
1. 最初に開くべきファイルはどれか。
1. 代表的な操作をしたとき、どの順で何が呼ばれ、何が保存されるか。
1. 境界値や異常な入力のとき、どうなるか。
1. 呼んでいる API の仕様と、その API が使う DB テーブルへ辿れるか。
1. 時間が経ってから振り返る人が、操作ごとの文書だけで、何を送ると何が返るかと、なぜそうしたかに答えられるか。

あわせて、関数ごとの仕様やテストケースの写しが紛れ込んでいないかを確かめる。

## 決定理由（Rationale）

- 関数ごとの約束をコメントに置くのは、Go の標準ライブラリや Rust のクレートと同じく、コードと仕様を同じ場所で更新させて食い違いを防ぐためである。React のように手書きのリファレンスを持つのは、利用者がソースを読まない外部の開発者で、保守する専任の担当がいる場合である。このプロジェクトの読者はソースを読むチームの人なので、前者に合わせる。
- 境界値や注意点などの振る舞いの詳細をコメントではなくテストを正とするのは、テストは実行されるのでコードから離れないためである。コメントに同じことを書くと、コードを直したときに片方だけが古くなる。考え方は [コードを書くときに意識すること](/knowledge/coding-mindset.md) の「テストを実行できる仕様書として書く」による。
- docs を全体像と「なぜ」に絞るのは、Diátaxis の分類でいう Explanation に当たり、1 つのファイルを読むだけでは分からない内容だからである。
- API と DB テーブルへのリンクを docs の中だけに張るのは、リンクを 1 か所で管理し、切れるリンクを増やさないためである。コードから読み始める人は `operationId` で検索すれば辿れる。コード側からの入り口が無くて困る場面が増えたら、JSDoc の `@see` や OpenAPI の `externalDocs` を足すことを検討する。
- この型は、既存の [ポモドーロ機能 仕様・データフロー](/frontend/features/pomodoro.md) のうち、シーケンス図と状態遷移図が振る舞いをよく伝えていた点を基にしている。
- 「機能が大きいとき」の分け方と図の使い分けは、ポモドーロ設定の文書（[概要](/backend/features/pomodoro-settings/overview.md)）を書いたときに決めた（2026-10-18）。1 つの文書に取得・保存・リセットの話が混ざると、初めて読む人がどの話がどの操作のものか分からなかった。
- 別の文書に詳しく書いた決定理由も、操作ごとの文書には要点を 1 文で書き、詳しい説明へリンクする。リンクだけにすると、振り返る人が理由を知るたびに別の文書を開くことになる。要点の 1 文は 2 か所に書くことになるが、詳しい説明は 1 か所に保つ。
