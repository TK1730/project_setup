# AI エージェントに好かれるコードベースの作り方

AI Hero の記事 [How To Make Codebases AI Agents Love][article]（Matt Pocock、2026-02-26 更新）の要約。AI エージェントの出力の質を最も左右するのはプロンプトや `AGENTS.md` ではなくコードベースの設計そのものであり、Deep Module（深いモジュール）で組むとよい、という主張である。

## 前提: AI は記憶のない新人である

記事は、AI を「超人的な開発者」ではなく「記憶を持たない新人」とみなす。エージェントを起動するたびに、映画『メメント』の主人公のように「ここはどこで、何をすればいいんだ」という状態からコードベースに入ってくる。1 日に 20 人以上の新人を送り込んでいるのと同じなので、コードベースは新人にとって辿りやすくなければならない。

## 設計が悪いと払う 3 つのコスト

| コスト               | 内容                                                                     |
| :------------------- | :----------------------------------------------------------------------- |
| フィードバックの遅さ | 変更が意図どおりに動いたかを、AI がすぐに知る手段がない                  |
| 辿りにくさ           | ファイルを探す、全体を理解する、テスト方法を知る、のいずれも難しい       |
| 人間の認知的な疲弊   | 人間が AI とコードベースの間に立ち、手作業で継ぎはぎする羽目になる       |

## AI に見えているもの

人間の頭の中では、モジュールは「サムネイル編集」「動画編集」「認証」「CRUD フォーム」のように、ゆるくまとまっている。しかし AI にはこのまとまりが見えない。AI に見えるのは、互いに自由に import し合える、ばらばらのモジュールの集まりである。ファイルシステムの構成も頭の中の地図と一致していなければ、手がかりにならない。

## 解決策: Deep Module

コードベースのファイル構成と設計を、人間の頭の中の地図に一致させる。そのための最良の方法として、記事は Deep Module を勧める。

Deep Module は書籍『A Philosophy of Software Design』（John Ousterhout）の概念で、「単純なインターフェースの裏に、多くの実装を持つモジュール」を指す。小さなモジュールを大量に並べる代わりに、単純で制御しやすいインターフェースを持つ大きな機能の塊を作る。外に公開するものは、必ずそのインターフェースを通す。

反対に、インターフェースの割に中身が薄いモジュールを Shallow Module（浅いモジュール）と呼ぶ。浅いモジュールが網の目のようにつながったコードベースは、辿りにくく、テストしにくく、頭に収まらない。

### Grey Box Module: 人間がインターフェースを、AI が実装を持つ

Deep Module のインターフェースは、コードベースに自然な継ぎ目（seam）を作る。

- インターフェースは人間が慎重に設計し、管理する。
- 中の実装は AI に任せる。
- モジュールの振る舞いをテストで固定する。テストが通る限り、中を見なくてよい。
- 中を見てもよい。好みを反映したいとき、結果に手を入れたいとき、性能を改善したいときは見る。

記事はこれを Grey Box Module と呼び、「インターフェースは人間のもの、実装は AI のもの、テストが両者を正直に保つ」とまとめている。

### 辿りやすさが上がる

- モジュールごとにフォルダを分け、明確な公開インターフェースを置く。
- AI はファイルシステムから全サービスを見渡し、型を読み、実装に潜らずに何をするモジュールかを理解できる。
- 複雑さを段階的に開示する（progressive disclosure）。インターフェースが入口にあってモジュールの役割を説明し、必要なときだけ中を見る。

### 人間の認知負荷が下がる

- 何百もの相互依存したモジュールではなく、7〜8 個の塊だけを頭に置けばよい。
- 塊の中身は AI が管理し、人間はインターフェースの設計と塊どうしの組み合わせだけを考える。
- これはバイブコーディングとは全く違う。どの処理をどのモジュールに入れるかという境界の判断には、人間のセンスが要る。

### 良い設計は昔から良い設計

記事は、これが新しい話ではないと強調する。20 年来、良いコードベースはこう設計されてきた。人間にとって良いものは、AI にとっても良い。

## まとめ（記事の結論）

- 多くのコードベースは、浅いモジュールの網になっていて、AI を迎える準備ができていない。
- 処方箋は、明確なインターフェースと強いテストを持つ Deep Module である。
- モジュールの境界は、PRD（要求仕様）から実装の Issue に至るまで一貫して考える。
- テストとフィードバックループは欠かせない。新人である AI が、自分の変更が動くかを知る唯一の手段だからである。
- 言語によって境界の強制しやすさは違う。著者は、TypeScript では境界を強制しにくいため、モジュール化を簡単にする [Effect][effect] を使うことが増えている、と述べている。

## 解説: 読み取れるポイント

記事の主張を、実践に移すときの観点として整理する。以下は記事そのものではなく、本要約での補足である。

- 「AI 向けの工夫」より「設計の基本」が効く。指示文やルールファイルを磨く前に、モジュールの境界・公開インターフェース・テストを整えるほうが、AI の出力への影響が大きい。
- 人間と AI の分担線はインターフェースに引く。人間はシグネチャ（名前・引数・戻り値）と責務を決め、テストで振る舞いを固定する。中身の実装は AI が書いても、テストが通る限り安全に任せられる。
- 機能単位のフォルダ分けは、Deep Module をファイルシステムに映す手段になる。技術レイヤー単位で分けると、1 つの機能が複数のフォルダに散らばり、AI に「まとまり」が見えにくい。[Package by Feature 設計指針](/knowledge/package-by-feature.md) と考え方が重なる。
- 「メソッドを短く」という原則と矛盾しない。Deep Module が求めるのは公開インターフェースを小さく単純にすることであり、内部を巨大な関数にすることではない。内部は [コードを書くときに意識すること](/knowledge/coding-mindset.md) に従って小さく保てる。
- テストは AI へのフィードバックループである。テストを振る舞いの仕様として書いておくと（[テスト設計における AAA パターン](/knowledge/aaa-pattern.md)、[テーブル駆動テストの設計指針](/knowledge/table-driven-tests.md)）、AI は変更のたびに自分で正しさを確かめられる。

## 用語

| 用語                   | 意味                                                                     |
| :--------------------- | :----------------------------------------------------------------------- |
| Deep Module            | 単純なインターフェースの裏に多くの実装を隠したモジュール                 |
| Shallow Module         | インターフェースの割に中身が薄いモジュール                               |
| Grey Box Module        | インターフェースは人間が設計し、実装は AI に任せ、テストで検証するモジュール |
| Seam（継ぎ目）         | 内側を差し替えても外側に影響しない境界                                   |
| Progressive Disclosure | 入口では概要だけを見せ、必要なときに詳細を開示する設計                   |
