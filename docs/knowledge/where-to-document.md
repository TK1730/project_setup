# 書く場所の選び方

伝えたいことを、どこに書くかの考え方をまとめる。
要点は、コードに近い手段から順に検討し、近い手段で伝えられることを遠い手段に回さないことである。
人とコンピューターの両方が分かるように書くことが目標であり、文書はその一部である。
内容は Google の docguide の Documentation Best Practices をもとにしている。

## 書く場所の一覧

短いコメントから長い文章まで、コードに近い順に並べる。

```mermaid
flowchart LR
  A[名前] --> B[インラインコメント] --> C[メソッドのコメント] --> D[クラス・ファイルのコメント] --> E[README] --> F[docs] --> G[設計文書] --> H[外部の文書]
```

| 書く場所                   | 書くこと                                                                                             |
| :------------------------- | :--------------------------------------------------------------------------------------------------- |
| 意味のある名前             | ローカル変数からクラス、ファイル、ディレクトリまで、名前で伝えられることはコメントや文書に回さない   |
| インラインコメント         | コードだけでは表せないこと。たとえば「なぜそのコードがあるか」                                       |
| メソッドのコメント         | メソッドが何をし、どう使うかという振る舞いの約束。引数、戻り値、注意点や制約、投げる例外や返すエラー |
| クラス・ファイルのコメント | 概要と短い使用例。使い方が複数あるときは、最も単純な使い方を先に置く                                 |
| `README.md`                | ディレクトリの案内。何を置く場所か、最初に見るべきファイル、誰が保守していてどこで詳しく知れるか     |
| docs                       | 使い始め方、テストの実行、出力のデバッグ、リリースの方法                                             |
| 設計文書・PRD              | 設計への意見を集めるために書く。実装後は決定の記録として扱う                                         |
| 外部の文書（wiki など）    | 使うなら、`README.md` などから分かりやすくリンクする                                                 |

## コメントとテスト

- コメントを書く前に、名前と構造で意図を伝えられないかを考える。
  考え方は [コードを書くときに意識すること](/knowledge/coding-mindset.md) の「コメントより読みやすいコードを優先する」を参照する。
- メソッドのコメントは、コードがどう振る舞わなければならないかの約束である。
  読み手は、そのコードを使ったり直したりする未来のプログラマーである。
  実用的に、短く書く（docguide の例えでは「これはハンマーだ。釘を打つのに使う。」）。
- 「なぜそう振る舞うか」は、使い方の理解に必要な場合を除き、インラインコメントに任せる。
- コメントに書いた振る舞いには、それを確かめるテストがあるのが妥当なことが多い。
  振る舞いの具体例、境界値、注意点は、実行できるテストで示す。
  考え方は同じ文書の「テストを実行できる仕様書として書く」を、テストの組み立て方は [テスト設計における AAA パターン](/knowledge/aaa-pattern.md) と [テーブル駆動テストの設計指針](/knowledge/table-driven-tests.md) を参照する。

## 設計文書を半分だけ正しい文書にしない

- 設計文書や PRD は、実装の前に意見を集めるためのものである。
- 実装が終わったら、決定の記録として扱う。
  実装と食い違ったまま、今の仕様を説明する文書として使わない。

## 同じことを書き直さない

- 共通の技術や手順の手引きを、自分で書き直さない。
  リンクする。
- 手引きが無い、またはひどく古い場合は、元の場所を更新するか、パッケージ単位の `README.md` を作る。
