# コードを書くときに意識すること

コードを書くときに意識してほしい心構えをまとめる。書く前に既存の解決策を探し、書くなら小さく、次に読む人が理解しやすいコードにし、振る舞いはテストで示す。内容は書籍『ソフトウェアエンジニアリングの基礎』の考え方を要約したものである。

## 車輪の再発明を避ける

書き始める前に、その問題がすでに解決されていないかを確かめる。数分の調査で、何時間もの作業を省けることがある。自分が初めてこの問題に向き合っている可能性は低い。

次の順に確かめる。

- 今のコードベースのどこかに、同じ処理をしている箇所はないか。
- 使っている言語の標準機能や標準ライブラリで実現できないか。言語は進化するので、知っている機能だけで判断しない。
- 使っているフレームワークに、すでに用意された方法はないか。
- プロジェクトがすでに依存しているライブラリで解決できないか。
- 解決しているオープンソースライブラリはないか。

新しいライブラリを入れるときは、そのライブラリが引き込む依存関係も調べる。サードパーティー製ライブラリの導入は、チームの方針と手順に従う。

## コードは少ないほどよい

コードベースが小さいほど、読む人が頭に入れる情報が減る。書かずに済むコードは書かない。

## 高凝集・低結合を保つ

コードを整理する手法の多くは、「高い凝集度と低い結合度」という原則（書籍では「コンピュータサイエンスの第ゼロ法則」と呼ぶ）に行き着く。この 2 つを満たすと、コードは読みやすく、変更しやすくなる。

- 凝集度: 1 つのモジュールの中の要素が、どれだけ密接に関係しているかの度合い。関係する要素がまとまっていれば凝集度が高い。印刷の処理を含む通知関数は、凝集度が低い例である。
- 結合度: モジュールや関数どうしが、どれだけ互いに依存しているかの度合い。結合度が高いと、一部の変更が無関係に見える箇所を壊す。通知サービスを変えただけで印刷モジュールが動かなくなる状態は、結合度が高い。

## 定型コードを避け、クラスを短く保つ

- 定型コード（ボイラープレート）は、エディタやフレームワークが生成したものでも、できるだけ減らす。
- クラスは短く保つ。適切な長さは言語によって違うが、読むのにスクロールが必要なら長すぎる可能性が高い。

## メソッドを短くし、1 つのことだけをさせる

- メソッドは短くする。1 桁の行数が理想である。
- 1 つのメソッドには 1 つのことだけをさせ、複数のメソッドを組み合わせて大きな処理を作る。Unix のコマンドラインツールと同じ考え方である。
- 名前に and や or などの接続詞が入るメソッドは、仕事を抱えすぎている。
- 名前を付けにくいメソッドも、仕事を抱えすぎている可能性が高い。分割してみる。
- 名前は、そのメソッドが何をするかを、凝った言い回しを使わずに短く表す。
- 重複したロジックは、少しであっても取り除く。

## 読み手のためにコードを書く

コードは、次にそれを読んで保守する人のために書く。「次の人の仕事を楽にするには、どう書けばよいか」「次の人に何を伝える必要があるか」を考える。

関数の適切な長さについては様々な考え方があるが、Martin Fowler は意図（何をするか）と実装（どうやるか）を分けることを勧めている（[Function Length][fowler-function-length]）。基準は「その関数が何をするかを理解するのに、どれだけ時間がかかるか」である。本体を読まなくても、名前だけで何をするかが分かるようにする。この考え方に従うと、数行や 1 行だけの関数になることも多い。クラス名は文脈を表し、メソッド名はそのクラスが何をするかを伝える。

コードは、新聞記事のように逆ピラミッド型で組み立てる。新聞記事は見出しとリード文で要点を伝え、後ろに行くほど詳しい背景になる。読者はどこで読むのを止めても要点をつかめる。

- クラス名は記事の見出しにあたる。
- クラス名とメソッドのシグネチャを眺めるだけで、大まかな内容が分かるようにする。
- 呼び出し先を細かく調べるのは任意であり、調べなくても要点が分かるようにする。

[fowler-function-length]: https://martinfowler.com/bliki/FunctionLength.html

## コメントより読みやすいコードを優先する

ここで扱うのは、処理を説明するインラインコメントである。関数・型・ファイルの使い方を利用者に伝える doc comment（JSDoc や Go の doc comment など）は、別のものとして扱う。

コメントを書く前に、名前と構造で意図を伝えられないかを考える。処理を説明するコメントを多く書くことは、コードスメル（設計に問題がありそうな兆候）である（[Code Smell][fowler-code-smell]）。

- 「何をしているか」は書かない。コードと同じ内容を繰り返すことになり、DRY 原則（Don't Repeat Yourself: 同じことを 2 か所に書かない）に反する。
- コードを直したときにコメントが更新されないと、コメントとコードが食い違い、後で読む人を混乱させる。
- コメントが必要だと感じたら、まずメソッド名や変数名を変える。多くの場合、それでコメントは要らなくなる。
- 便利でも分かりにくい言語機能（いわゆる「魔法」）は避ける。
- 分かりにくい処理をどうしても簡潔にできないときだけ、「なぜそうしたか」を書く。複数の候補からそのアルゴリズムを選んだ理由や、特に複雑なロジックの説明がこれにあたる。
- 説明が必要なコードは、コメントを足す前に、書き直せないかを考える。

[fowler-code-smell]: https://martinfowler.com/bliki/CodeSmell.html

## テストを実行できる仕様書として書く

振る舞いの具体例は、コメントではなくテストに書く。コメント、README、仕様書は、一度書くとコードから離れていく。テストはコードと一緒に実行されるので、コードとともに更新され続ける実行可能な仕様書になる。

- テストの名前は、対象が「何をすべきか」を表す文にする。BDD（振る舞い駆動開発）の考え方で、テストの一覧を読むだけで仕様が分かるようになる（[Introducing BDD][dan-north-bdd]）。
- テストがあれば、安心してリファクタリングできる。品質に自信が持て、後からコードを触る人の道しるべにもなる。
- 既存のコードの動きを調べて理解したら、その理解をテストとして残す。学んだことが記録され、他の人も使える。
- コードを触るたびに、名前を直す、不要なコードを消すなどして、触る前より良い状態にして残す。

[dan-north-bdd]: https://dannorth.net/blog/introducing-bdd/

### コンシューマ駆動契約で API の約束をテストにする

コンシューマ駆動契約（Consumer-Driven Contracts）は、API の利用側（コンシューマ）が期待する振る舞いを契約としてテストに書き、提供側がそのテストを実行して約束を守っていることを確かめる手法である（[Consumer-Driven Contracts][fowler-cdc]）。テストを、サービス間の約束を示すドキュメントとして使う。

- 提供側は、契約を破らない限り、下流のシステムを壊す心配をせずにコードを変えられる。
- 利用側は、期待する振る舞いを確かめるテストがあるので、サービスを信頼でき、自分のコードも安心して変えられる。
- 多くの言語やフレームワークに、この手法を支えるツールがある。サービス間に API がある場合は活用する。

[fowler-cdc]: https://martinfowler.com/articles/consumerDrivenContracts.html
