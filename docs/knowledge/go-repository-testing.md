# Go の Repository 層のテストの設計指針

Repository 層のテストは、SQL が本物のスキーマに対して正しく動くかを確かめるためにある。そのため、偽物ではなく本物の DB に対して実行する。DB への接続はテスト用の小さなヘルパーにまとめる。テストデータはテストごとに一意な ID で分けて、終わったら消す。確かめるのは「自分が書いた SQL の動き」だけにして、DB が保証していることは確かめない。

## 1. DB 接続のヘルパー

同じ接続の手順を、テスト関数ごとに写さない。テスト用のパッケージにヘルパーを 1 つ作り、各テストは 1 行で呼ぶ。

```go
db := testdb.Open(t)
```

| 項目                | 指針                                                                              | 理由                                                                                                                                                |
| :------------------ | :-------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------- |
| 置き場所            | `internal/testdb`（DB だけなら）、`internal/testutil`（テスト用の部品が増えたら） | `internal/` の下は、同じモジュールの中からしか import できない。テスト専用の部品を外に出さずに済む                                                  |
| 名前                | `testdb.Open(t *testing.T) *sql.DB`                                               | パッケージ名と続けて読んで「テスト用の DB を開く」と分かる                                                                                          |
| 最初に `t.Helper()` | 呼ぶ                                                                              | 失敗したときに、ヘルパーの中ではなく、呼び出したテストの行が表示される[^go-testing]                                                                 |
| 失敗したとき        | `t.Fatal`                                                                         | 準備の失敗は、それ以上テストを続けられない失敗である[^google-best-practices]                                                                        |
| 接続の確認          | `sql.Open` のあとに `PingContext` を呼ぶ                                          | `sql.Open` は接続を作らず、引数を確かめるだけのことがある。接続できるかは `Ping` で確かめる[^go-database-sql]                                       |
| 後片付け            | `defer` ではなく `t.Cleanup` で `Close` を予約する                                | `defer` はヘルパーを抜けた時点で実行され、閉じた DB を返してしまう。`t.Cleanup` はテストとそのサブテストが全部終わったときに実行される[^go-testing] |

ヘルパーの手順は次のとおりである。

1. `t.Helper()` を呼ぶ
2. 接続文字列を決める（環境変数があればそれを、なければ既定値を使う）
3. `sql.Open` で開く
4. `PingContext` で接続できるかを確かめ、だめなら `t.Fatalf`
5. `t.Cleanup` で `Close` を予約して返す

## 2. テストデータの分け方

| 方式                                            | 内容                                          | 長所                                                     | 短所                                                                                                                          |
| :---------------------------------------------- | :-------------------------------------------- | :------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------- |
| A. 一意な ID                                    | テストごとに `test_<ULID>` のような ID を使う | ほかのテストやパッケージとぶつからない。並列にしても安全 | 消し忘れると行が残る                                                                                                          |
| B. `t.Cleanup` で消す                           | A の行を、テストの終わりに `DELETE` する      | 単純で、本番のコードの形を変えずに済む                   | 予約する前に `Fatal` すると残る。`DELETE` のエラーを捨てると、残っても気づけない                                              |
| C. テストごとにトランザクションを張って巻き戻す | テストの最後に `tx.Rollback()` する           | 何も残らない                                             | Repository が `*sql.Tx` も受け取れるように、型を変える必要がある                                                              |
| 全行を消す（`TRUNCATE`）                        | テーブルを空にする                            | 確実に空になる                                           | `go test ./...` はパッケージを並列に実行する[^go-cmd]。同じ DB を使うほかのテストのデータまで消すので、共有の DB では使えない |

まずは A と B を組み合わせる。B の注意点は 2 つある。

- `t.Cleanup` は、行を作る**前**に予約する。予約より前に `Fatal` すると、行が残る。
- `DELETE` のエラーは `_, _ =` で捨てずに、`t.Errorf` で知らせる。

C が要るのは、Repository が自分でトランザクションを使うようになったときである。そのときは、`*sql.DB` と `*sql.Tx` に共通するメソッド（`ExecContext`・`QueryRowContext` など）[^go-transactions] だけを持つ小さなインターフェイスを、Repository が受け取るようにする。sqlc が生成する `DBTX` が、よく知られた例である[^sqlc-transactions]。

## 3. どの DB に対して実行するか

| 選択肢                                   | 長所                                                     | 短所                                                       |
| :--------------------------------------- | :------------------------------------------------------- | :--------------------------------------------------------- |
| 開発用の DB を共有する                   | 準備が要らない                                           | 手で入れた開発用のデータと、テストのデータが混ざる         |
| テスト専用の DB（同じサーバーの別の DB） | 安く分けられる                                           | マイグレーションを 2 つの DB に当てる手間が増える          |
| testcontainers-go                        | 毎回まっさらな DB で動き、どこで実行しても同じ結果になる | Docker が必要。依存が増え、起動が遅くなる[^testcontainers] |

- **接続文字列**: 「環境変数があればそれを、なければ既定値を使う」形にする。手元ではそのまま動き、CI では差し替えられる。
- **DB のないところで飛ばす**: `testing.Short()` が真なら `t.Skip` する[^go-testing]。`go test -short` で DB のテストを飛ばせる。接続に失敗したときは、既定では `Fatal` にする。`Skip` にすると、DB を起動し忘れても成功に見えて、テストしていないことに気づけない。
- **結果のキャッシュ**: `go test` は成功した結果を覚えていて、`(cached)` と表示して実行しないことがある。DB の中身はキャッシュのキーに含まれないので、DB のテストは `-count=1` を付けて実行する[^go-cmd]。

## 4. 確かめること・確かめないこと

**確かめること**

- SQL が本物のスキーマに対して正しく動くこと
- 書き込んだあと、DB から読み直して保存されたことを確かめる。戻り値だけでは、保存された証明として弱い。読み直しは生の `SELECT` がいちばん独立している
- 前提のデータは、テスト対象のメソッドではなく、生の `db.Exec` で入れる。テスト対象で準備すると、そのバグが前提の段階で混ざり、どこが壊れたか分からなくなる
- 「行がない」などのエラーが、決めたとおりに返ること（例: `errors.Is(err, sql.ErrNoRows)`）
- 制約（CHECK など）の違反は、制約ごとに代表の 1 ケース。値の境界の網羅は、範囲チェックを持つ層（Usecase など）のテストで行う
- 削除は「行が実際に消えたこと」と、仕様によっては「行がなくてもエラーにならないこと」の 2 つ

**確かめないこと**

- DB そのものの保証（1 文の原子性、`ON CONFLICT` の同時実行の安全性、型の変換など）
- 送った SQL の文字列そのもの。文字列が合っていても、本物の DB で正しく動く保証にはならない
- 本番の DB に対する実行

## 5. 並列実行と TestMain

- **パッケージの間はもともと並列**である[^go-cmd]。テーブルや ID がパッケージごとに別なら問題ない。
- **パッケージの中の `t.Parallel()`** は、一意な ID（方式 A）と `t.Cleanup` での `Close` がそろっていれば付けられる。ただし速くなる量は小さいので、最初は付けなくてよい。
- **`TestMain`** は、パッケージの全テストに共通の準備と後片付けがあるときに使う。ただし、最初に選ぶ方法ではない。準備は、それが必要なテストだけに限る[^google-best-practices]。
- **`t.Context()`** は、Cleanup が呼ばれる直前にキャンセルされる[^go-testing]。テスト本体の SQL には使えるが、Cleanup の中の `DELETE` には使えない。

## Rationale（決定理由）

- Repository のテストを本物の DB で行うのは、SQL の誤りが Go のコンパイルでは見つからず、DB に送って初めて分かるためである。
- 接続をヘルパーにまとめるのは、写した手順の一部（`Ping` や `Close` の時期）を直すときに、1 か所で済ませるためである。
- データの分け方を一意な ID と `t.Cleanup` から始めるのは、本番のコードの形を変えずに、ほかのテストとぶつからない状態を作れるためである。トランザクションで巻き戻す方式は、必要になってから採る。
- 確かめる範囲を「自分が書いた SQL の動き」に絞るのは、DB の保証を確かめても、テストが遅く壊れやすくなるだけで、見つかる間違いが増えないためである。
