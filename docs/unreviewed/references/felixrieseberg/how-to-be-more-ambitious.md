# モデルと働く人間のための「もっと野心的になる」方法

Felix Rieseberg の記事 [How to be more ambitious: A tutorial for humans with models][article]（2026-10-13 公開）の要約。AI モデルの能力を生かしきれない原因は、モデルよりも人間が頼む内容の小ささにある、と記事は主張する。そのうえで、頼み方を Altitude（抽象度）・Depth（深さ）・Range（幅）の 3 方向に広げる具体的な方法を示す。

- 著者: Felix Rieseberg（Anthropic のエンジニアリングマネージャー。Claude.ai、Cowork、Claude Code Desktop のエンジニアリングを率いる。Electron の共同メンテナー）
- 本文書は全訳ではなく、記事の見出し順に沿った要約である。引用は原文のまま「引用:」と明示する。

## 導入: 野心の 4 つの種類

著者は Claude の開発に携わりながら、自分でも思いつかなかった、または試していなかった使い道に出会い続けているという。例として、アマチュア天文学者の新しい惑星の発見を Claude が手助けしたらしい話、著者が気に入っている AI 製のミュージックビデオ、「数学の新しい時代」をめぐる議論を挙げる。

モデルの能力は分野ごとにばらつきがある。記事は Terence Tao の「ある方向では驚異的だが、別の方向では不十分」という評を引いている。

> 引用: "Model capabilities don't grow uniformly."

この能力をうまく使う人がいる一方、簡単な質問以上の使い道を見つけられない人もいる。著者は、人はもっと野心的になるべきだと述べ、野心を次の 4 種類に分ける。

| 種類     | 意味                                     |
| :------- | :--------------------------------------- |
| Speed    | 同じ仕事をより短い時間でこなす           |
| Altitude | より高い抽象度で、成果を目標にして頼む   |
| Depth    | 一流の専門家と同じ道具・方法・知識で頼む |
| Range    | 複数の分野にまたがる取り組み方で頼む     |

Speed は AI の経済的価値の中心だが、すでに広く知られており、取り組み方に工夫がほとんど要らないため、記事では扱わない。

## Altitude: 抽象度を上げる

Altitude の野心とは、目の前の 1 つの作業ではなく、その先の成果に焦点を当てて頼むことである。問うべきは「次に何が起きるべきか」「言われた目標のさらに先の目標は何か」である。

著者自身の例では、個々のクラッシュを直すよう Claude に頼むのをやめ、アプリがクラッシュしない状態を保つよう頼むようになった。

### 四半期業務レビュー資料の例

架空の企業 Acme Inc の四半期業務レビュー（QBR）の資料を例に、抽象度を段階的に上げた 3 つの頼み方を示す。

1. 今期に何が変わり、なぜ変わり、何をすべきかを説明させる。生データをできるだけ多くモデルに渡す。
1. 最も急ぐ判断を 3 つ挙げさせ、それぞれに賛成と反対の論点を下書きさせる。
1. レビューの進め方そのものを設計し直させる。会社の過去の経緯に当てはめて、新しい進め方なら問題をもっと早く見つけられたことを示させ、1 四半期は旧来の進め方と並行して運用させる。

### Altitude が向く仕事と限界

- 向くのは成果で評価される仕事であり、創作的な仕事には向かない。その仕事に会議が必要になりそうなら、Altitude が合っている兆しである。
- 限界もある。2026 年時点では「お金を稼いでこい」とだけ頼んでもうまくいかない。ただし、モデルが改善するにつれて、より高い抽象度を扱えるようになっている。

### 人間を繰り返しのループから外す

長く続く仕組み（durable workflow）を作り、繰り返し作業から人間を外す。クラッシュしないアプリの例では、著者は次の準備をした。

- クラッシュレポートを簡単に取得できるようにする。
- アプリのバージョンと git のコミットを対応付ける。
- Windows・macOS・Linux のマシンを Claude に使わせ、クラッシュの再現と修正の確認をさせる。

## Depth: 専門家の深さで頼む

Depth の野心とは、その分野の一流の専門家と同じ道具・方法・知識を使わせ、専門家がその結果から学べるほどの水準まで押し進めることである。

### 解約分析の例で示す手法

Acme Inc の顧客の解約（churn）分析を例に、次の手法を挙げる。

- 業界標準の道具を使わせる。Markdown の表で済ませず、データベースや統計モデルを使わせる。
- 無茶な目標を、妥当な目標として伝える。たとえば表示に 5 秒かかるサイトに対して 200 ミリ秒を求める。
- 前提を生データで確かめさせる。たとえば、解約の原因が本当にオンボーディング（使い始めの導線）にあるのかを検証させる。
- 新しい知見を生み出させる。ログから顧客の振る舞いを模擬し、まだ知られていない最も早い解約の兆候を探させ、その予測を未使用のデータで検証させる。
- 外部の判定者を使う。理想はモデルが自分で実行してすぐに結果を得られる道具であり、モデル自身に採点させない。

> 引用: "Do not ask the model to judge itself."（原文では not が強調されている）

### 頼み方そのものを深くするプロンプト

記事は、依頼文をモデル自身に書き直させるプロンプトを紹介している。モデルに次の点を洗い出させ、それを踏まえて依頼文を書き直させる。

- 一流の専門家なら、依頼された内容を超えて何をするか
- 専門家が使う、最も生に近い一次資料は何か
- 専門家が使う具体的な方法と道具は何か
- 結果の正しさを裏付ける外部の証拠は何か

## Range: 複数の分野にまたがる

Range の野心とは、これまで現実的だった以上に多くの分野を横断して仕事に取り組むことである。オーケストレーター（全体を指揮するエージェント）やサブエージェントを使うマルチエージェント構成が、これを容易にする。

著者の同僚 Alex Albert は、Claude に Blender を使わせて室内デザインをレンダリングしていた。著者はビデオゲームを作った経験があるのに、自分のホームページ用の 3D 空間を Claude に作らせることを思いつかなかったという。

### Range を広げる手法

- 名詞を動詞に置き換える。Tom Kelley と Jonathan Littman の『The Art of Innovation』の考え方である。「資料」を、「忙しい人に因果関係の物語を信じてもらうこと」と言い換えると、取り組み方の選択肢が広がる。
- 視点の異なる「チーム」を集める。アナリスト、ジャーナリスト、編集者、モーションデザイナー、オーディオデザイナーに加え、敵対的に検証するレッドチームとして空売り投資家と不正調査の会計士を置く。
- ロールプレイをさせない。役割の文体をまねさせるのではなく、その役割が実際に行う仕事をさせる。

> 引用: "Don't ask the model to write like a short seller, ask it to do what a short seller does to research their position."

### 前提となる環境

これらにはすべて、ソフトウェアをインストールできるなどモデルが自由に使えるコンピューターと、コネクターなどを通じた関連データへのアクセスが必要である。

## We have been here before: 人類は前にもここにいた

人間は昔から、可能だと信じる範囲と、自分を信頼できる狭い専門分野に縛られてきた。彫刻家だったミケランジェロも、当初はシスティーナ礼拝堂の天井画を描くことに抵抗した。

### 自己効力感と目標設定

- 心理学ではこれを自己効力感（self-efficacy、自分にはできるという感覚）と呼ぶ。
- Locke と Latham による 35 年分の目標設定研究のレビューでは、具体的で難しい目標のほうが「ベストを尽くせ」よりも成果が高かった。
- Patrick Collison の「Fast」リストは、大胆な目標と厳しい期限のもとで成し遂げられた事例を集めている。

### 記録に残る事例

- 1939 年、George Dantzig は黒板の 2 つの問題を宿題だと思って書き写した。実際は統計学の未解決問題で、彼はそれを解いた。
- 1954 年 5 月に Roger Bannister が 1 マイル 4 分の壁を破ったあと、彼が唯一の達成者だったのは 46 日間だった。また 2026 年 4 月のロンドンでは Sabastian Sawe が公式に初めてマラソンで 2 時間を切り、同じレースの 2 位の選手も 2 時間を切った。
- 『The Inner Game of Tennis』は、力みすぎると成績が下がると説く。著者は、Linux が「ただの趣味」として発表されたことも思い起こしている。

### 記事の結論

自己効力感は古い問題だが、AI の能力が数週間ごとに進歩する今、その影響はより大きくなっている。著者は、読者に他の手法があれば共有してほしいと呼びかけて記事を締めている。

> 引用: "Self-efficacy isn't a new problem, but it is a more powerful one now."
