# 長時間動くエージェントのための効果的なハーネス

Anthropic のエンジニアリングブログの記事 [Effective harnesses for long-running agents][article]（Justin Young、2025-11-26 公開）の要約。
何時間・何日もかかる開発をエージェントに任せると、作業は別々のセッションに分かれ、新しいセッションは前の記憶を持たない。
記事は、この問題を Claude Agent SDK の上で解くハーネスの組み方を、claude.ai のクローンを作る実験をもとに説明している。

[article]: https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents

## 問題：記憶のないセッションの交代

- エージェントは別々のセッションで動き、新しいセッションは前に何があったかの記憶なしで始まる。
  記事は、引き継ぎメモなしで交代勤務するエンジニアにたとえている。
- コンテキストを圧縮する仕組み（compaction）だけでは足りない。
  Opus 4.5 を Agent SDK のループで動かしても、大まかな依頼文だけでは本番品質の Web アプリを作り切れなかった。

観察された失敗は 2 つある。

1. 一度に多くをやろうとして、実装の途中でコンテキストが尽き、作りかけで説明のない機能が残る。
1. プロジェクトの後半で、エージェントが既存の進捗を見て、早すぎる段階で「完成」と宣言する。

## 解決策：2 種類のエージェント

| エージェント             | 動く回数               | 仕事                                                                                 |
| ------------------------ | ---------------------- | ------------------------------------------------------------------------------------ |
| 初期化エージェント       | 最初のセッションで 1 回 | 環境を用意する。`init.sh`、進捗ファイル、機能一覧、最初の git コミットを作る         |
| コーディングエージェント | 2 回目以降の毎セッション | 1 機能ずつ進め、終わるときにコードを main に入れられるきれいな状態にして記録を残す |

2 つのエージェントの違いは、最初のユーザープロンプトだけである。
システムプロンプト、ツール、ハーネスは同じものを使う。

## 状態を引き継ぐファイル

| ファイル               | 役割                                                                         |
| ---------------------- | ---------------------------------------------------------------------------- |
| 機能一覧（JSON）       | 依頼文から展開した機能の一覧。完了の定義になる                               |
| `claude-progress.txt`  | 各セッションが何をしたかのログ                                               |
| `init.sh`              | 開発サーバーを起動するスクリプト。エージェントが起動方法を調べ直さずに済む |
| git の履歴             | 説明つきのコミット。悪い変更を戻し、動く状態に復帰するのに使う             |

### 機能一覧

- claude.ai のクローンの例では、200 以上の機能を並べ、すべて「未達成」から始めた。
- 各機能は、説明、確認の手順、`passes` フィールドを持つ。
- コーディングエージェントが変えてよいのは `passes` だけである。
  プロンプトで、テストを消したり書き換えたりすることを強く禁じている。
- Markdown ではなく JSON にしたのは、モデルが JSON を不適切に書き換えたり上書きしたりしにくいためである。

## セッションの始め方

コーディングエージェントは、毎回同じ手順で状況をつかむ。

1. 作業ディレクトリを確かめる。
1. git のログと進捗ファイルを読み、最近の作業を把握する。
1. 機能一覧を読み、未完了で優先度の最も高い機能を 1 つ選ぶ。
1. `init.sh` で開発サーバーを起動し、基本的な E2E の確認をする（チャットの例では、メッセージを送って返事が来るか）。
   前のセッションが壊した状態を、新しい作業を始める前に見つけるためである。

## テスト

- Claude は、E2E で確かめないまま機能を完了にすることが多かった。
  単体テストや `curl` による確認では、通して動かしたときの不具合を見落とした。
- ブラウザ自動化（Puppeteer の MCP サーバー）を使い、人間のユーザーと同じ操作で確かめるよう指示すると、結果が大きく良くなった。
- 限界もある。
  Claude は Puppeteer 経由でブラウザ標準のアラートのモーダルを見られないので、それに頼る機能は不具合が多くなった。

## 失敗と対策の一覧

| 失敗                                 | 初期化エージェントの対策            | コーディングエージェントの対策                                       |
| ------------------------------------ | ----------------------------------- | -------------------------------------------------------------------- |
| 早すぎる「完成」宣言                 | 機能一覧を作る                      | 機能一覧を読み、1 機能だけ選んで取り組む                             |
| 不具合や説明のない状態が残る         | git リポジトリと進捗ファイルを作る | 始めに進捗ファイルと git ログを読んで基本の確認をし、終わりにコミットと進捗の記録をする |
| テストせずに機能を完了にする         | 機能一覧を作る                      | 自分で丁寧に確かめてから `passes` にする                             |
| アプリの起動方法を調べるのに時間がかかる | `init.sh` を書く                    | セッションの始めに `init.sh` を読む                                  |

## 今後の課題

- 汎用のコーディングエージェント 1 つが最良か、テスト・QA・コードの片付けなどに分けた複数のエージェントが良いかは、まだ分かっていない。
- 実験は Web アプリのフルスタック開発に絞っている。
  記事は、科学研究や金融モデリングなど、ほかの長時間タスクにも応用できる可能性があると述べている。
