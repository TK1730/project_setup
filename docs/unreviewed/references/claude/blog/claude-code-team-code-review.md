# Claude Code チームのコードレビューの進め方

claude.dev ブログ（Engineering）の記事 [How the Claude Code team does code review][article]（Addy Osmani、Morgan Westlee Lunt、Qing Wang、2026-10-15 公開）の要約。エージェントがコードの大半を書くようになった Anthropic の Claude Code チームが、レビューをやめずに「読む作業」の多くを機械へ移し、間違いをすぐ戻せる仕組みに投資した、という報告である。見出しの順は記事に合わせている。

## 前置き: 何が変わったか

- Claude Code 自身のコードは、約 90% を Claude が書いている。
- 6 月から 9 月で、マージされた PR は 2 倍を超えて増えた。一方で、差し戻し（revert）が必要になった PR の割合は 40% 以上減った。
- 著者らはレビューをなくしたのではない。読む作業の多くを機械に任せ、人の時間と注意を節約する方向に最適化し、間違いを速く簡単に戻せるようにした、と述べる。

> 引用: "We didn't remove review."

## コードレビューの目的を考え直す

- Anthropic のモノレポに入る変更は、5 月の 1 日約 2,500 件から、9 月には 1 日 30,000 件超に増えた。Claude Code は別リポジトリだが、同じ圧力を受けている。
- コードレビューには 2 つの役割がある。1 つは出荷前に問題を見つけて直すこと、もう 1 つはチーム内で文脈を共有することである。記事は主に前者を扱う。
- レビューは、書きながら動くスペルチェックのように、常に回り続けるものになった。多くの変更は、人が見る前に Claude が少なくとも 1 回レビューして直している。

> 引用: "Most review now happens before a PR exists."

## 足りない資源は人の時間と注意

- 目標は、差し戻しやインシデントを増やさずに、ほとんどの PR を人が多くても 1 人だけ関わる形でマージすることである。
- 測る指標は、PR ごとの人の承認数（中央値と 95 パーセンタイル）、人のコメント数、PR が人を待っている時間である。
- 差し戻し率とインシデント率はガードレール（超えてはいけない線）として扱う。これらが上がれば、人の時間を節約したのではなく、別の場所へ移しただけになるためである。

## 変更がたどる道筋

記事の図 A は、1 つの変更が通る道筋を示す。

1. PR を出す前の検証。
1. すべての PR に対する必須の CI、Claude によるコードレビュー、セキュリティレビュー。
1. リスクに応じた承認とマージキュー。
1. マージ後のフィーチャーフラグ、段階的なリリース、監視と前向き修正（fix-forward）またはロールバック。

道筋の大部分は自動化されており、リスクが最も高いところでだけ人が判断する。

## 層ごとの仕組み

図 B は、各層が一部の問題を捕まえ、一部を見逃すことを示す。最後に残ったものはロールバックで受け止める。

### 層 1: 他の人が見る前に検証する

- Claude には、実行できるもの（テスト、ビルド、スクリーンショット）を与え、「成功した」と主張させるのではなく出力を見せさせる。その後、新しい文脈を持つサブエージェントが差分をレビューする。
- 社内のスキルで、バグの確認、差分の簡素化、端から端までの振る舞いのテストを行う。UI の変更はデザインガイドラインと照らし合わせる。
- Boris Cherny は、検証を入れると結果が 2〜3 倍良くなると見積もっている（記事内の引用として紹介）。
- レビューで繰り返し出る指摘は、元の場所で直す。スキル、lint ルール、指示ファイルがその場所である。
  - `CLAUDE.md`: プロジェクトのスタック、規約、目標と目標外を書く。短く保つ。
  - `REVIEW.md`: コードオーナーが書く。良い `REVIEW.md` は、そのリポジトリで何が失敗にあたるかを書き、細かい指摘（nit）の数に上限を設け、見なくてよいパスを挙げ、指摘にはファイルと行の根拠を求める。レビューの要約は件数から始める。

### 層 2: すべての PR に AI レビューを行う

- Claude は、差分をリポジトリ全体と PR の意図に照らしてレビューする。バグ修正では根本原因まで確かめる。
- リサーチプレビューの後、実質的な指摘コメントが付く社内 PR の割合は 16% から 54% に上がった。1,000 行を超える PR の大半には指摘が付き、小さい PR の大半は指摘なしで戻る。
- リポジトリごとに Quick、Standard、Deep の深さを選ぶ。Deep は、バグを見逃したときの損失が大きい場所に使う。
- 複数のエージェントが並列でバグを探し、別のエージェント群が各指摘に投票する。十分な合意を得た指摘だけを投稿し、スタイルだけの指摘は捨てる。これらの絞り込みは社内 PR で A/B テストした。
- 指摘には Important、Nit、Pre-existing のラベルを付ける。前からあったバグを作者のせいにしないためである。
- すべての指摘は、直すか、理由を付けて解決済みにしなければならない。

### 層 3: マージを止められるセキュリティレビュー

- バグのレビューとは別に、自動のセキュリティレビューを行う。どちらかのレビューに未解決の指摘があれば、マージできない。
- 後のコミットで直れば、指摘は自動で解消される。使う道具として、オープンソースのセキュリティレビュー GitHub Action と `/security-review` コマンドが挙げられている。

### 層 4: マージを止める自動チェック

- lint、型チェック、全プラットフォームでのテスト、ビルドを行う。一般的な CLI の PR では数十のチェックが走る。
- PR テンプレートでは、どうテストしたか、どう元に戻すかを尋ねる。依頼者が最終確認をする。

### 層 5: リスクに応じた人の承認

| リスク | 例                                                                 | 必要な人の承認                         |
| :----- | :----------------------------------------------------------------- | :------------------------------------- |
| 低     | ドキュメント、文言、社内向け機能、フラグの裏に隠した追加だけの変更 | 自動チェックとセキュリティが通れば不要 |
| 中     | 通常のプロダクト変更、キャッシュ・自動更新・システムプロンプトなど | 1 人                                   |
| 高     | 最もリスクの高いコード、常に 2 人が必要なパス                      | 2 人                                   |

- リスクの段階は、作者ではなく変更の中身から分類器が決める。2 つ目の分類器が、それでも人が必要かを確かめる。CI のワークフローファイルなど、常に人が必要なパスもある。
- 軽い経路を使えるのは、信頼された作者（主にそのコードを持つチーム）だけである。
- エージェントの承認は、人の承認として数えない。
- エージェントに指示を出した人は、必須のレビュアーとして数える。
- 承認は特定の 1 コミットに対してだけ有効である。

> 引用: "The change sets the tier, not the author."

### 層 6: マージキュー、フラグ、段階的なリリース

- マージキューは、変更を当てた最新の main に対してチェックを再実行する。
- 新しい振る舞いはフラグの裏に隠して出し、まず Anthropic の社員に使ってもらう。公開リリースは先に `latest` チャンネルへ出し、`stable` は後から追う。

### 層 7: 速い検知と速いロールバック

- フラグはデプロイなしで切れる。Claude Code には週替わりのオンコール当番があり、インシデントの振り返りでは「どの層で捕まえるべきだったか」を問う。
- 指標が動いたときに自動で承認を厳しくする仕組み（サーキットブレーカー）はまだない。人が関わらないマージを増やす前に、これを入れたいとエンジニアは考えている。

## レビュアーを良くする方法

図 C は改善のループを示す。インシデントと差し戻しを、専門家が確かめた評価（eval）のケースにする。評価は毎日実行する。レビュアーのプロンプト、ツール、モデルを変えるたびに全ケースで採点し、点が上がった変更だけを残す。

- ノイズの測り方: コメントを作者の反応（直した、異議を唱えた、意図どおりだった、問題ではなかった）で分類する。さらに、問題がないと分かっている PR にもレビュアーを走らせ、害のある誤検知を数える。優先順位は、まず本物のバグを捕まえること、次にレビューの往復回数を減らすことである。
- 収束しない問題: ある CLI の PR は、一晩で 50 回を超えるレビューの往復を繰り返した。`git blame` で調べると、レビュアーが指摘し続けた内容の約 59% は、最初のレビューの時点から既にあったコードだった。
- 対策:
  - 往復回数に上限を設ける。3 回を過ぎたら一歩引いて、やり方そのものを考え直す。
  - 最初の数回の後は、新しい差分だけを再レビューする。
  - 1 行ではなく、バグの種類として指摘する。
  - 既に投稿した指摘を繰り返さない。
  - 夜間に動くレビューエージェントが、既存のコードも走査する。
- 図 D の結果（社内 PR、対策前 → 対策後）:

| 指標                             | 対策前 | 対策後 |
| :------------------------------- | :----- | :----- |
| 1 回のレビューと修正で通った割合 | 65%    | 78%    |
| 5 回以上の往復が必要だった割合   | 8.9%   | 1.5%   |
| 通るまでのレビュー回数の平均     | 2.08   | 1.32   |

## 人がループに残る場所

図 E は、人に残す 5 つの判断を挙げる。

1. そもそもこれを作るべきか（方向性、センス、範囲）。
1. リスクの高いコード（課金、自動更新、CI のワークフロー）。
1. 他の人が真似することになる設計。
1. 証拠を読むこと（テストの出力、コマンド、スクリーンショット、指摘）。
1. 結果に責任を持つこと。

## チームで文脈を共有する

- 決まった手順はない。エンジニアは、コードベースの特定の部分について Claude に解説を書かせる。数分ででき、今のコードの姿をそのまま反映する。自分の学び方に合った図を Claude に作らせる人もいる。
- 1 行の文言変更を読んでも学べることは少ない。変更するモジュールの解説を読むほうが多くを学べる。
- 公開の Slack チャンネルで、他の人の作業をその場で見られるようにしている。

## 「マージした人が持ち主」

- 変更は小さく保ち、すべてを元に戻せるようにする。影響範囲（blast radius）の大きさでレビューの厳しさを決める。
- 退行（regression）は、テレメトリと社内での利用から見つかる。
- 自分の変更を自分で直すのがチームの習慣である。これは責めることではなく、インシデントの振り返りでは仕組みのほうを調べる。
- 持ち主であることは公開チャンネルを通じて共有され、持ち主以外からもフィードバックが来る。

## 方向を変えるとき

- エージェントのおかげで作業を始めるのは安くなったので、マージすべきでない PR も出てくる。たいていはチャンネルの誰かが懸念やもっと簡単な道を挙げ、作者が PR を閉じるか作り直す。
- 速く書いた PR を閉じても、損をした気にはならない。方向の変更は、完成した PR へのブロッキングコメントとしてではなく、スレッドの早い段階で持ち出す。

## このやり方を取り入れる方法

記事の最後のチェックリストを、段階ごとにまとめる。

### PR を出す前

- エージェントが実行できるチェックを短い `CLAUDE.md` に書き、フォーマッタと linter のフックを用意する。
- `/code-review` と `/security-review` を手元で実行するか、新しい文脈のサブエージェントにレビューさせる。
- `REVIEW.md` を置き、繰り返し出るレビューの指摘をそこへ移す。

### すべての PR で

- CI を必須にする。PR テンプレートに「Testing」「Risk」「How to revert」の欄を足す。
- AI レビュアー（Code Review for Claude Code、または Claude Code GitHub Action）を 1 つのリポジトリに入れ、数週間 `REVIEW.md` を調整してから広げる。
- 自動のセキュリティレビューを足し、すべてのスレッドが解決するまでマージできないようにする。
- レビューの深さをリスクに合わせる。往復回数に上限を設け、最初の数回の後は新しい差分だけを再レビューする。

### 人の承認の決め方

- リスクの段階を、作者ではなく変更の中身で決めるように書く。最初は厳しくし、根拠が集まってから緩める。
- 軽い経路は信頼された作者に限る。CODEOWNERS とブランチ保護で、重要なパスには必ず人が必要になるようにする。
- ボットの承認を、必須の人の承認の代わりにしない。新しいコミットが来たら承認を取り消す。

### マージとその後

- マージキュー、フィーチャーフラグ、社内での先行利用、段階的なリリース、1 手順でのロールバックを使う。
- インシデントと差し戻しを評価用のデータにし、レビュアーを変えるたびに採点し直す。
- 人の時間を測り、差し戻しとインシデントをガードレールにする。

## これからの方向

- Code Review の発表では、PR を承認するのは引き続き人の判断であり、製品は承認ではなく指摘を投稿するとしている。Anthropic 自身のリポジトリでは、どの低リスクの変更を自動チェックだけでマージするかをオーナーが決めており、その線は動き続けている。
- レビューが何かを見逃したときは、モデルに何が足りなかったかを問い、その答えを `CLAUDE.md`、スキル、新しいチェックのいずれかに入れる。
- 目指すのは、変更 1 件あたりの人の時間を減らし、差し戻しを今より増やさないことである。

## コードレビューの用語

- 差し戻し（revert）: マージした変更を取り消すこと。
- ガードレール指標: 改善を狙う指標ではなく、悪化させてはいけない指標。
- マージキュー: マージ待ちの変更を順に並べ、最新の main に当てた状態でチェックしてからマージする仕組み。
- フィーチャーフラグ: デプロイせずに機能の有効・無効を切り替える設定。
- 評価（eval）: モデルやプロンプトの性能を測るための、決まったテストケースの集まり。
